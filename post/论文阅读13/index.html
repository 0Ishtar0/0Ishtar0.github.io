TTAPose

背景介绍

TTAPose 研究的是未见物体位姿估计，训练阶段未见过目标物体，但测试时给出该物体的 CAD 模型和 RGB-D 图像，要求估计物体相对于相机的 6D 位姿：

$$ T=[R\mid t]\in SE(3) $$

其中：

  • $R\in SO(3)$：物体的三维旋转；
  • $t\in\mathbb{R}^3$：物体的三维平移。

本文使用的基础模型是 MatchU。它先在 CAD 模型点云和观测点云之间预测 3D-3D 对应关系，再根据对应点求解位姿。

设 CAD 模型点云为：

$$ \mathcal{P}=\{p_i\in\mathbb{R}^3\mid 1\le i\le n\} $$

从深度图得到的局部观测点云为：

$$ \mathcal{Q}=\{q_j\in\mathbb{R}^3\mid 1\le j\le m\} $$

MatchU 使用旋转不变的特征提取与融合，将 CAD 点云特征与 RGB-D 观测特征对齐。模型预测对应点集合：

$$ \mathcal{C}=\{(p_i,q_j)\} $$

最终位姿通过点云配准得到：

$$ T^*=\arg\min_{T\in SE(3)} \sum_{(p_i,q_j)\in\mathcal{C}} \|Tp_i-q_j\|_2^2 $$

研究动机

针对6D位姿估计设计的TTA方法很少，且此前TTA-COPE为类别级方法。

核心困难是：

  • 无标签目标图像没有可靠的真实对应关系；
  • 直接最小化预测熵可能放大错误匹配；
  • teacher 生成的初始伪标签也会受到遮挡、形状差异和传感器噪声影响；
  • 位姿估计是几何问题，仅在输出概率上做置信度优化并不足以保证几何一致性。

TTAPose 的核心思路是：用 teacher-student 网络完成测试时自适应，再通过几何位姿优化增强 teacher 的伪对应标签。

方法

合成数据预训练

对应关系的熵最小化

TTAPose 首先将分类任务中的 TENT 思想迁移到点云对应关系预测。

对每个 CAD 点 $p_i$，模型预测它与观测点 $q_j$ 构成对应关系的条件概率：

$$ P(\mathcal{C}(p_i,q_j)\mid p_i) $$

测试时通过最小化对应分布的熵，让模型对点匹配作出更加确定的预测：

$$ \mathcal{L}_{E}=-\sum_{i=1}^{n}P(\mathcal{C}(p_i,q_j)\mid p_i)\log P(\mathcal{C}(p_i,q_j)\mid p_i) $$

Teacher-Student 自适应

teacher 和 student 使用相同的网络结构，并都由合成数据上的预训练权重初始化：

$$ \theta_T^{(0)}=\theta_S^{(0)}=\theta_{\text{pre}} $$

给定无标签目标图像 $x_t$，teacher 和 student 分别输出对应关系：

$$ \mathcal{C}_T=\theta_T(x_t),\qquad\mathcal{C}_S=\theta_S(x_t) $$

teacher 的预测被作为 student 的伪标签，student 使用与预训练阶段相同的匹配损失学习：

$$ \mathcal{L}_{\text{pl}}^S=\mathcal{L}(\theta_S(x_t),\mathcal{C}_T) $$

student 的完整测试时损失为：

$$ \mathcal{L}_{\text{TTA}}=\lambda\mathcal{L}_{\text{pl}}^S+(1-\lambda)\mathcal{L}_{E} $$

其中实验中取 $\lambda=0.5$。

student 通过反向传播正常更新，teacher 则通过EMA方式从 student 中吸收信息。实验中动量系数取：

$$ \mu=0.99 $$

伪标签增强

TTAPose 先将teacher提出的位姿进行优化，随后再映射回对应关系进行监督。

完整过程如下：

  1. teacher 从 CAD 点云和观测点云中预测初始对应关系 $\mathcal{C}_I^T$；
  2. 从对应关系中采样并计算多个 6D 位姿假设；
  3. 使用 ICP 根据三维几何继续优化位姿；
  4. （可选）使用 MegaPose 结合 RGB 图像和三维点云对候选位姿进一步优化；
  5. 选择置信度最高的位姿作为增强后的伪位姿；
  6. 将增强位姿重新投影为对应关系 $\mathcal{C}_R^T$，用于监督 student。

可以把这个过程写成：

$$ \mathcal{C}_I^T \rightarrow \{T_1,T_2,\ldots,T_h\} \rightarrow T_R \rightarrow \mathcal{C}_R^T $$

其中 $T_R$ 是经过 ICP 和 MegaPose 优化、重排后的最终伪位姿。

在线与离线适配

TTAPose 支持两种部署方式：

设置 使用的数据 参数更新方式
Offline TTA 测试前收集的一批目标物体无标签 RGB-D 图像 先适配，再固定模型测试
Online TTA 测试流中连续到来的真实 RGB-D 图像 推理与参数更新同步进行

实验

数据集与评价指标

源域预训练使用 GSO 数据集，约 80 万张 RGB-D 合成训练图像；

目标域测试使用三个真实 6D 姿态估计基准：

  • LM-O：遮挡较严重的场景；
  • T-LESS：大量弱纹理且存在对称性的工业物体；
  • YCB-V：真实杂乱环境中的日常物体。

论文采用 BOP 的 Average Recall：

$$ AR= \frac{ AR_{\text{VSD}} +AR_{\text{MSSD}} +AR_{\text{MSPD}} }{3} $$

其中：

  • VSD：可见表面差异；
  • MSSD：考虑对称性的最大三维表面距离；
  • MSPD：考虑对称性的最大二维投影距离。

为了和 seen-object 方法比较，论文还报告 ADD(-S)。当平均模型点误差小于物体直径的 10% 时，预测被认为正确；对称物体使用最近点距离。

消融实验

论文在 LM-O 上验证各组件的作用：

删除或替换的组件 ADD(-S) 下降 说明
删除 entropy minimization 0.3 熵损失提供辅助正则，但不是主要增益来源
删除 pseudo-label enhancement 1.8 下降最大，几何增强是核心组件
删除最终 pose refinement 1.1 refinement 有效，但弱于将增强伪标签用于持续训练
动量 teacher 改为直接更新 1.4 直接同步更新容易造成训练不稳定
删除全部 TTA 组件 2.9 各组件存在互补作用

EvoMAS

背景介绍

EvoMAS 研究的是如何自动生成一个 LLM-based Multi-Agent System（MAS）。

一个多智能体系统不仅包含若干 agent，还需要同时确定：

  • 每个 agent 的角色和 system prompt；
  • 每个 agent 使用的 backbone LLM；
  • 每个 agent 可以调用哪些工具；
  • agent 之间如何通信；
  • 哪些 agent 接收原始任务，哪些 agent 输出最终答案；
  • 整个系统如何执行和终止。

传统方法通常由人手工设计固定的组织形式，例如：

1

Planner → Worker → Reviewer → Finalizer

或者：

1

多个 agent 独立解题 → Debate / Majority Vote → 输出答案

这些系统在某类任务上有效，但很难保证同一种拓扑、prompt 和模型分配在推理、软件工程、工具调用等任务上都合适。

研究动机

自动生成 MAS 的已有方法主要存在两类问题。

第一类：直接生成可执行代码。

例如让 LLM 直接生成一个完整的 multi-agent program。它具有较大的结构搜索空间，但容易产生：

  • 语法错误；
  • 缺失依赖或接口不匹配；
  • agent 间消息格式不一致；
  • 运行时异常；
  • 针对某个 benchmark 的脆弱代码。

第二类：限制在固定模板内搜索。

这种方式执行更稳定，但通常只能修改 prompt、角色或少量连接关系，表达能力不足，也难以针对不同任务改变模型、工具和拓扑。

EvoMAS 的认为多智能体系统（MAS）应该针对每个任务由结构化配置生成，再在执行时实例化。

问题定义

论文将一个 MAS 配置定义为：

$$ C=(G,\{A_i\}_{i=1}^{k},V_{\text{in}},V_{\text{out}}) $$

其中通信图为：

$$ G=(V,E) $$
  • $V=\{v_1,\ldots,v_k\}$：agent 节点集合；
  • $E\subseteq V\times V$：有向通信边；
  • $(v_i,v_j)\in E$ 表示 $v_i$ 的输出会成为 $v_j$ 的部分输入；
  • 图被限制为无环图，从而保证执行过程可以稳定调度。

每个 agent 的配置为：

$$ A_i=(b_i,p_i,\Gamma_i) $$

其中：

参数 含义
$b_i$ agent 使用的 backbone model
$p_i$ agent 的 system prompt 模板
$\Gamma_i$ agent 可以访问的工具集合

$V_{\text{in}}$ 表示接收原始任务的输入 agent，$V_{\text{out}}$ 表示产生最终答案的输出 agent。

给定任务 $q$，执行过程记为：

$$ \operatorname{Exec}(C,q) $$

EvoMAS 的目标是为每个任务找到使奖励最大的配置：

$$ C_q^*=\arg\max_{C}R(q,C) $$

方法

EvoMAS 维护两个可以跨任务积累的状态：

  1. candidate configuration pool：保存已有 MAS 配置；
  2. experience memory：保存过去任务中的演化轨迹总结。

对于每个新任务，系统先从配置池选择若干起点，然后执行、评价并进行多轮进化，最后把最优配置和经验写回系统。

操作 作用
Select 从配置池检索与当前任务最相关、能力互补的候选配置
Mutate 根据执行反馈，局部修改一个配置
Crossover 组合两个父配置中的有效结构和 agent 属性
Consolidate 将演化过程压缩为可复用经验并写入 memory

配置池初始化

初始 pool 由已有的人类设计 MAS 作为种子，包括：

  • Peer Review；
  • Cross-team Orchestration；
  • Multi-Agent Debate；
  • Majority Vote；等

这些配置包含不同协作结构，使进化从可执行且具有基本协作能力的系统开始。

Select：选择初始配置

设当前配置池为 $\mathbb{C}$。给定任务 $q$，Select 选出 $k$ 个初始候选：

$$ \{C_1,\ldots,C_k\}= \operatorname{Select}(q,\mathbb{C}) $$

选择过程会参考：

  • 配置的任务描述；
  • 域标签；
  • 在相似历史任务上的表现；
  • 当前任务需要的能力。

meta-model 不只选择最相似的一个配置，还会尽量保留互补性。例如一个候选擅长任务分解，另一个候选擅长验证。选出后，meta-model 会针对当前任务改写 agent 角色和 prompt，形成 任务特点的初始种群。

Mutate：反馈驱动的局部变异

设配置 $C_i$ 在任务 $q$ 上的执行轨迹与反馈为：

$$ \tau_q(C_i) $$

经验记忆为 $\mathbb{E}$，则变异操作为：

$$ C_i'= \operatorname{Mutate} (C_i,\tau_q(C_i),\mathbb{E}) $$

meta-model 首先从执行轨迹中诊断主要瓶颈，然后每次只修改一种组件：

  • agent prompt；
  • backbone model；
  • tool list；
  • communication topology。

例如：

1
2

执行反馈：最终答案经常遗漏边界条件
变异：新增 verifier，或强化 reviewer prompt

又例如：

1
2

执行反馈：工具调用正确，但推理步骤质量不足
变异：把 verification agent 从较小模型替换为更强的推理模型

Crossover：配置交叉

给定两个父配置 $C_i$ 和 $C_j$：

$$ C_{ij}'= \operatorname{Crossover} (C_i,C_j,\tau_q(C_i),\tau_q(C_j),\mathbb{E}) $$

具体操作为：

  1. 从一个父配置完整继承通信拓扑；
  2. 在该拓扑的各个位置上，重新组合两个父配置的 prompt、model 和 tool；
  3. 根据两个父配置的执行轨迹，优先继承已经被证明有效的 agent 属性。

执行、评价与选择

从 $k$ 个初始配置开始，EvoMAS 最多进行 $n$ 次演化。每一步执行：

  1. 从当前候选集合选择表现较好的父配置；
  2. 执行 mutation 或 crossover 得到后代；
  3. 在当前任务上运行新配置；
  4. 使用奖励函数评价；
  5. 将后代加入候选集合。

最终候选集合包含 $k+n$ 个配置，并返回奖励最高的一个。

配置的奖励定义为：

$$ R(q,C)=\operatorname{Metrics}(q,C)-\beta\operatorname{Cost}(C) $$

其中 $\operatorname{Metrics}(q,C)$ 由 LLM-as-a-judge 根据任务类型，从正确性、完整性和推理质量等维度评价。

单次 MAS 执行成本定义为：

$$ \operatorname{Cost}(C)=T+\alpha L $$

其中：

  • $T$：总 token 使用量；
  • $L$：wall-clock latency，单位为秒；
  • $\alpha=1000$：将延迟换算到统一成本尺度；
  • $\beta$：性能与成本之间的权衡系数。

Pool 与 Experience Memory 更新

任务按顺序到来。第 $t$ 个任务完成后，最优配置 $C_q$ 被加入配置池。并且使用 LLM 将演化轨迹压缩成经验摘要并保存进memory。

后续每次演化检索 3 至多条与当前任务描述最相似的经验。

实验

本工作不需要模型训练，所有Agent通过api调用实现，agent之间的通信方式为把上一个 agent 的文本输出放进下一个 agent 的 上下文。

数据集与指标

论文覆盖三种类型的 agentic benchmark：

Benchmark 任务类型 指标
BBEH 多步推理与工具增强问题求解 Accuracy
SWE-Bench-Lite / Verified 真实软件工程 issue 修复 Resolved Rate
WorkBench 办公规划、工具调用与多步执行 Accuracy

此外，作者使用 Execution Rate（ER） 衡量生成的 MAS 能否在没有结构错误和运行时错误的情况下成功执行：

$$ ER= \frac{\text{成功执行的生成系统数}} {\text{生成系统总数}} $$

每个任务运行 3 次并取平均结果。

默认使用 Claude-4-Sonnet 作为生成配置的 meta-model。agent backbone 候选池包括：

  • Claude-3.5-Sonnet；
  • Qwen3-235B-A22B；
  • Qwen3-Coder-480B-A35B。

在 BBEH 和 WorkBench 上，single-agent baseline 使用 SmolAgent 的 CodeAgent；在 SWE-Bench 上使用 SWE-Agent。

主结果

执行可靠性

EvoMAS 的配置生成方式保持了很高的执行率：

Benchmark Execution Rate
BBEH 98.9%
BBEH-Mini 98.2%
WorkBench 98.5%
SWE-Bench-Lite 96.8%
SWE-Bench-Verified 98.4%

作为对比，直接生成代码的 MAS-GPT 在 BBEH 上执行率为 71.5%，在 SWE-Bench-Lite 上仅为 1.2%。

这验证了 configuration generation 的核心优势：生成器只负责声明 agent、prompt、model、tool 和 topology，运行时解释器负责保证执行，因此不会频繁出现代码语法和框架接口错误。

更强模型下的结果

使用 Claude-4.5-Sonnet 同时作为 generator 和 agent backbone 时，EvoMAS 在 SWE-Bench-Verified 上达到：

$$ 79.1\% $$

论文指出，该结果略高于写作时公开榜单最高的 78.8%。更重要的是，在 Claude-3.5、Claude-4 和 Claude-4.5 三代模型上，EvoMAS 相对 single agent 和固定 MAS 的提升仍然存在，说明 evolutionary MAS generation 与底层模型能力是互补关系。

初始配置池与演化深度

在 BBEH-Mini 和 WorkBench 上的消融如下：

配置 BBEH-Mini WorkBench
Empty pool，$T=5$ 33.5 —
Default pool，$T=1$ 44.4 45.4
Default pool，$T=3$ 49.1 48.9
Default pool，$T=5$ 47.6 48.3

高质量初始配置池在 BBEH-Mini 上带来 15.6 个百分点的提升。演化深度也不是越大越好，$T=3$ 优于 $T=5$，说明过多迭代存在收益递减，并可能引入不必要的结构变化。

即使禁止跨任务累积，仅在当前任务内部做演化，EvoMAS 也能从 single agent 的 36.6% 提升到 40.4%，说明增益不完全依赖历史 memory。

Meta-model 与奖励信号

固定 agent backbone pool，仅替换生成配置的 meta-model，在 SWE-Bench-Verified 上得到：

Meta-model Resolved Rate
Qwen3-235B 58.2%
Claude-3.5-Sonnet 56.4%
Claude-4-Sonnet 63.8%
Claude-4.5-Sonnet 67.4%
最佳非 EvoMAS baseline 50.2%

即使使用较弱 meta-model，EvoMAS 仍然超过非 EvoMAS baseline，说明主要收益来自演化框架，而不是绑定某个特定 generator。

LLM-as-a-judge 与使用真实标签的 oracle reward 对比如下：

Reward BBEH-Mini WorkBench SWE-Bench
LLM-as-a-Judge 44.4 48.9 63.8
Oracle Ground Truth 47.8 50.4 66.9
差值 +3.4 +1.5 +3.1

oracle reward 更好，但提升幅度有限，说明不访问真实答案时，LLM judge 已经可以提供有效的进化方向。

演化出的结构规律

作者观察到若干不在初始配置池中显式定义的 emergent pattern：

  • model-role affinity：更强的推理模型常被分配给 verification 角色，而不是平均分配到所有 agent；
  • functional specialization：系统会自然形成专门的 decomposer、solver 和 verifier；
  • novel topology：进化会产生不同于任何种子家族的新拓扑，部分任务中 agent 数量减少约 70%；
  • 阶段性修改：早期主要优化 prompt，中期更换 model，后期才修改 topology；
  • mutation 与 crossover 分工：mutation 适合早期针对单一错误局部修复，crossover 则在不同配置形成互补能力后更有效。

不同任务也会触发不同的变异偏好：

任务类型 Prompt Model Topology
一般推理任务 50.6% 28.1% 21.3%
对模型容量敏感的任务 32.7% 44.6% 22.7%
需要任务分解的任务 35.2% 23.1% 41.7%

这一结果支持联合优化 prompt、model 和 topology 的设计：不同任务的主要瓶颈并不相同，只搜索其中一个维度会限制最终性能。

测试时计算量

EvoMAS 的提升不是简单来自重复调用更多 token。论文在 SWE-Bench-Verified 上进行了 budget-matched comparison：

方法 Tokens Accuracy
Claude-3.5-Sonnet Single Agent 2.3M 33.6%
Loop，匹配 EvoMAS 预算 29M 33.6%
Best-of-6 + selection 24M 37.0%
Best-of-10 + selection 40M 37.8%
EvoMAS 29M 42.7%

在 Claude-4.5-Sonnet 下，相同的 31M token 预算中：

方法 Accuracy
Loop 71.4%
EvoMAS 79.1%

说明关键并不是 token 数量本身，而是如何把计算分配到分解、执行、验证和聚合等不同角色中。

另一方面，EvoMAS 的绝对成本仍然很高。meta-model 占总 token 的 7.7%、总时间的 10.6%；主要成本来自多次 MAS 实际执行。作者发现配置池大约在处理 300—400 个 query 后趋于稳定，此后可以减少演化，仅执行 configuration selection 和一次最终 MAS，从而摊薄前期搜索成本。

总结

EvoMAS 的核心贡献可以概括为三个层次：

  1. 表示层：用结构化配置表示 MAS，而不是直接生成可执行代码；
  2. 搜索层：用执行反馈驱动 selection、mutation 和 crossover；
  3. 记忆层：通过配置池与经验 memory 跨任务复用成功结构。

它的主要优点是：

  • 配置生成比代码生成具有更高的 executability；
  • 可以同时搜索角色、prompt、model、tool 和 topology；
  • 能根据具体任务动态决定多智能体结构；
  • 能积累跨任务经验，并随着任务流逐渐改进；
  • 与更强的基础模型和更多 test-time compute 具有互补性。

它的局限包括：

  • 前期需要多次完整执行候选 MAS，token 与时间成本较高；
  • 演化依赖 LLM-as-a-judge，judge 的偏差可能影响搜索方向；
  • 默认配置是有向无环协作图，不覆盖持续循环、长期状态或对抗式 agent；
  • 顺序处理任务并不断扩充 pool 和 memory，会增加长期检索和维护成本；
  • benchmark 上找到的结构能否稳定迁移到开放、动态的真实环境，仍需要进一步验证。

总体来看，EvoMAS 并不是简单地“让多个 agent 多讨论几轮”，而是把多智能体系统本身当成测试时可优化的对象。论文最有价值的观点是：随着 LLM 推理能力增强，test-time scaling 不只可以发生在单个模型的思维链或采样次数上，也可以发生在整个 agent organization 的结构搜索上。
